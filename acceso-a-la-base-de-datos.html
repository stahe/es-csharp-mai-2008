    9. Acceso a la base de datos

    9.1. Conector ADO.NET

    Echemos otro vistazo a la arquitectura por capas utilizada en diversas ocasiones

    En los ejemplos estudiados, la capa [dao] ha utilizado hasta ahora dos tipos de fuentes de datos:

    • datos codificados de forma fija
    • datos de archivos de texto

    En este capítulo, estudiamos el caso en el que los datos proceden de una base de datos. La arquitectura de tres capas evoluciona entonces hacia una arquitectura multicapa. Existen varios tipos de arquitectura multicapa. Estudiaremos los conceptos básicos con lo siguiente:

    En el diagrama anterior, la capa [dao] [1] se comunica con el SGBD [3] a través de una biblioteca de clases específica para el SGBD utilizado y que se suministra junto con él. Esta capa implementa funciones estándar conocidas como ADO (Active X Data Objects). A dicha capa se la denomina «proveedor» (en este caso, «proveedor de acceso a la base de datos») o incluso «conector». La mayoría de los SGBD cuentan ahora con un conector ADO.NET, lo que no ocurría en los inicios de la plataforma .NET. Los conectores .NET no ofrecen una interfaz estándar para la capa [dao], por lo que esta última incluye los nombres de las clases del conector en su código. Si se cambia el SGBD, se cambia el conector y las clases, y hay que modificar la capa [dao] . Esto resulta a la vez eficiente, ya que el conector .NET, al haber sido escrito para un SGBD concreto, sabe cómo utilizarlo de la mejor manera posible, y rígido, ya que cambiar el SGBD implica cambiar la capa [dao]. Este segundo argumento debe ponerse en perspectiva: las empresas no cambian de SGBD con mucha frecuencia. Veremos más adelante que, desde la versión 2.0 de .NET, existe un conector genérico que aporta flexibilidad sin sacrificar el rendimiento.

    9.2. Las dos formas de utilizar una fuente de datos

    La plataforma .NET permite explotar una fuente de datos de dos formas diferentes:

    1. modo conectado
    2. modo sin conexión

    En el modo conectado, la aplicación

    1. abre una conexión con la fuente de datos
    2. trabaja con la fuente de datos de lectura/escritura
    3. cierra la conexión

    En modo sin conexión, la aplicación

    1. abre una conexión con la fuente de datos
    2. obtiene una copia en memoria de todos o parte de los datos de origen
    3. cierra la conexión
    4. trabaja con la copia en memoria de los datos de lectura/escritura
    5. cuando el trabajo ha finalizado, abre una conexión, envía los datos modificados a la fuente de datos para que se tengan en cuenta y cierra la conexión

    Aquí solo estudiaremos el modo conectado.

    9.3.2. Los cuatro comandos básicos del lenguaje SQL

    SQL (Structured Query Language) es un lenguaje parcialmente estandarizado para consultar y actualizar bases de datos. Todos los SGBD respetan la parte estandarizada de SQL, pero añaden extensiones propias al lenguaje que aprovechan ciertas características de los SGBD. Ya hemos visto dos ejemplos: la generación automática de claves primarias y los tipos permitidos para las columnas de las tablas suelen depender del SGBD.

    Los cuatro comandos básicos del lenguaje SQL que presentamos están estandarizados y son aceptados por todos los SGBD:

    select col1, col2,...
from table1, table2,...
where condición
ordenar por expresión
...
    La consulta que recupera los datos contenidos en una base de datos. Solo las palabras clave de la primera línea son obligatorias; las demás son opcionales. Aquí se incluyen otras palabras clave que no se muestran.
    1. Se realiza una unión con todas las tablas que siguen a la palabra clave from
    2. Solo se conservan las columnas que siguen a la palabra clave select
    3. Solo se conservan las filas que cumplen la condición where
    4. Las filas resultantes, ordenadas por la expresión de la palabra clave order by, forman el resultado de la consulta. Este resultado es una tabla. 
    insert into table(col1,col2, ...)
values (val1,val2, ...)
    Inserta una línea en la tabla. (col1, col2, ...) especifica las columnas de la fila que se inicializarán con los valores (val1, val2, ...).
    actualizar tabla
establecer col1=val1, col2=val2
where condición
    Actualiza la tabla comprobando la condición (todas las filas si no hay where). Para estas filas, col1 recibe el valor val1
    eliminar de la tabla

    Elimina todas las condiciones de comprobación de la tabla

    9.3.3. Interfaces básicas de ADO.NET para el modo conectado

    Volvamos al diagrama de una aplicación que utiliza una base de datos a través de un conector ADO.NET:

    En el modo conectado, el :

    1. abre una conexión con el origen de datos
    2. trabaja con el origen de datos de lectura/escritura
    3. cierra la conexión

    Hay tres interfaces de ADO.NET que se ocupan principalmente de estas operaciones:

    • IDbConnection, que encapsula las propiedades y métodos de la conexión.
    • IDbCommand, que encapsula las propiedades y los métodos del comando SQL que se está ejecutando.
    • IDataReader, que encapsula las propiedades y métodos del resultado de una instrucción SQL SELECT.

    9.3.7. Ejecución de una consulta SELECT

    La ejecución de órdenes SQL requiere los siguientes pasos:

    1. Conexión a la base de datos
    2. Envío de órdenes SQL a la base
    3. Procesamiento de los resultados de la consulta SQL
    4. Cierre de la conexión

    Los pasos 2 y 3 se repiten, y la conexión solo se cierra cuando la base de datos ya no se utiliza. Las conexiones abiertas son recursos limitados de un SGBD. Deben conservarse. Por eso siempre intentamos limitar la duración de una conexión abierta. En este ejemplo, la conexión se cierra tras cada comando SQL. Se abre una nueva conexión para la siguiente orden SQL. Abrir y cerrar una conexión es costoso. Para reducir este coste, algunos SGBD ofrecen el concepto de grupos de conexiones abiertas: cuando se inicializa la aplicación, se abren N conexiones y se asignan al grupo. Permanecen abiertas hasta el final de la aplicación. Cuando la aplicación abre una conexión, recibe una de las N conexiones ya abiertas en el grupo. Cuando cierra la conexión, simplemente la devuelve al grupo. La ventaja de este sistema es que resulta transparente para el desarrollador: no es necesario modificar el programa para utilizar el grupo de conexiones. La configuración del grupo de conexiones depende del SGBD.

    9.4.5. Conector genérico

    La arquitectura utilizada será la siguiente:

    Al igual que los conectores ODBC y OLE DB, el conector genérico ofrece una interfaz estándar a las aplicaciones que lo utilizan, pero mejora el rendimiento sin sacrificar la flexibilidad. El conector genérico se basa en los conectores SGBD propietarios. La aplicación utiliza clases del conector genérico.     9.4.6. ¿Qué conector elegir?

    Volvamos a la arquitectura de una aplicación de base de datos:

    Hemos visto varios tipos de conectores ADO.NET:

    • los conectores propietarios son los más eficientes, pero hacen que la capa [dao] dependa de clases propietarias. Cambiar el SGBD implica cambiar la capa [dao].
    • Los conectores ODBC u OLE DB permiten trabajar con múltiples bases de datos sin cambiar la capa [dao]. Son menos potentes que los conectores propietarios.
    • El conector genérico se basa en conectores propietarios, al tiempo que presenta una interfaz estándar para la capa [DAO].

    Así pues, parece que el conector genérico es el conector ideal. Sin embargo, en la práctica, el conector genérico no consigue ocultar todas las particularidades de un SGBD tras una interfaz estándar. En el siguiente párrafo, veremos el concepto de consultas parametrizadas. Con SQL Server, una consulta parametrizada tiene la siguiente forma:

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    Con MySQL5, la misma consulta se escribiría así:

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    Por lo tanto, hay una diferencia en la sintaxis. La propiedad de interfaz IDbCommand, descrita en el apartado 9.3.3, es la siguiente:

    Parámetros
    la lista de parámetros de una orden SQL parametrizada. La orden update articles set price=price*1.1 where id=@id tiene el parámetro @id.

    El tipo de la propiedad Parameters es IDataParameterCollection, una interfaz. Representa todos los parámetros de la instrucción SQL CommandText. La propiedad Parameters tiene un método Add para añadir IDataParameter, que también es una interfaz. Tiene las siguientes propiedades:

    • ParameterName: nombre del parámetro
    • DbType: el tipo SQL del parámetro
    • Value: el valor asignado al
    • ...

    El tipo IDataParameter es muy adecuado para parámetros del orden SQL 

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    ya que contiene parámetros con nombre. Se puede utilizar ParameterName.

    El tipo IDataParameter no es adecuado para la orden SQL 

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    porque los parámetros no tienen nombre. En ese caso, se tiene en cuenta el orden en que los parámetros se añaden a la colección [IDbCommand.Parameters]. En este ejemplo, los 4 parámetros deben insertarse en el siguiente orden: nombre, precio, stockactuel, stockminimum. En una consulta con parámetros con nombre, el orden en que se añaden los parámetros es irrelevante. Al final, el desarrollador no puede ignorar por completo el SGBD que utiliza al inicializar los parámetros de una consulta parametrizada. Esta es una de las limitaciones actuales del conector genérico.

    Existen marcos de trabajo que superan estas limitaciones y añaden nuevas funcionalidades a la capa [dao]:

    Un marco de trabajo es un conjunto de bibliotecas de clases diseñado para facilitar una forma concreta de diseñar la arquitectura de una aplicación. Existen varios marcos de este tipo, que permiten escribir capas [dao] que son a la vez de alto rendimiento e insensibles a los cambios en el SGBD:

    • Spring.Net [http://www.springframework.net/], ya presentado en este documento, ofrece el equivalente al conector genérico estudiado, sin sus limitaciones, así como diversas facilidades para simplificar el acceso a los datos. También hay disponible una versión en Java.
    • iBatis.Net [http://ibatis.apache.org] es más antiguo y completo que Spring.Net. Hay disponible una versión en Java.
    • NHibernate [http://www.hibernate.org/] es una adaptación de la versión Java de Hibernate, mundialmente famosa. NHibernate permite que la capa [dao] se comunique con el SGBD sin emitir comandos SQL. La capa [dao] trabaja con objetos Hibernate. Se utiliza un lenguaje de consulta HBL (Hibernate Query Language) para consultar los objetos gestionados por Hibernate. Son estos objetos los que emiten los comandos SQL. Hibernate puede adaptarse a los sintaxis SQL de los SGBD.
    • LINQ (Language INtegrated Query), integrado en la versión 3.5 de .NET y disponible en C# 2008. LINQ sigue los pasos de NHibernate, pero por el momento (mayo de 2008) solo es compatible con el SGBD SQL Server. Esto debería evolucionar con el tiempo. LINQ va más allá que NHibernate: su lenguaje de consulta permite realizar consultas estándar de tres tipos diferentes de fuentes de datos:
      • colecciones de objetos (LINQ to Objects)
      • un archivo XML (LINQ to XML)
      • una base de datos (LINQ to SQL)

    Estos marcos no se tratarán en este documento. Sin embargo, recomendamos encarecidamente su uso en aplicaciones profesionales.

    9.6. Transacciones

    9.6.1. General

    Una transacción es una secuencia de órdenes SQL ejecutadas «atómicamente»:

    • o bien todas las operaciones se realizan correctamente
    • o bien falla alguna de ellas, en cuyo caso se cancelan todas las anteriores

    Al final, las operaciones de una transacción se han aplicado todas con éxito o ninguna. Cuando el usuario tiene el control de la transacción, la valida con un comando COMMIT o la cancela con un comando ROLLBACK.

    En nuestros ejemplos anteriores, no utilizamos una transacción. Y, sin embargo, sí lo hicimos, porque en un SGBD una orden SQL siempre se ejecuta dentro de una transacción. Si el cliente .NET no inicia él mismo una transacción de forma explícita, el SGBD utiliza una transacción implícita. Hay dos casos habituales:

    1. cada orden SQL individual es objeto de una transacción, iniciada por el SGBD antes de la orden y cerrada después. Decimos que estamos en modo autocommit. Así que es como si el cliente .NET estuviera realizando transacciones para cada orden SQL.
    2. el SGBD no está en modo autocommit e inicia una transacción implícita en la primera orden SQL que el cliente .NET emite fuera de una transacción y deja que el cliente la cierre. Todas las órdenes SQL emitidas por el cliente .NET forman entonces parte de la transacción implícita. Esto puede terminarse por diversos eventos: el cliente cierra la conexión, inicia una nueva transacción, etc., pero entonces se está en una situación dependiente del SGBD. Este modo debe evitarse.

    El modo predeterminado suele establecerse al configurar el SGBD. Algunos SGBD tienen como valor predeterminado el autocommit, otros no. Por defecto, SQL Server Compact está en modo autocommit.

    Las órdenes SQL de diferentes usuarios se ejecutan al mismo tiempo en transacciones que funcionan en paralelo. Las operaciones realizadas por una transacción pueden afectar a las realizadas por otra. Existen cuatro niveles de aislamiento entre las transacciones de diferentes usuarios:

    • Lectura sin confirmar
    • Lectura confirmada
    • Lectura repetible
    • Serializable

    Lectura no confirmada

    Este modo de aislamiento también se conoce como «lectura sucia». A continuación se muestra un ejemplo de lo que puede ocurrir en este modo:

    1. un usuario U1 inicia una transacción en una tabla T
    2. un usuario U2 inicia una transacción en la misma tabla T
    3. el usuario U1 modifica filas en la tabla T, pero aún no las valida
    4. el usuario U2 «ve» estas modificaciones y toma decisiones basándose en lo que ve
    5. el usuario cancela la transacción con un ROLLBACK

    Podemos ver que en el punto 4, el usuario U2 ha tomado una decisión basándose en datos que más tarde resultarán ser falsos.

    Lectura confirmada

    Este modo de aislamiento evita el problema anterior. En este modo, el usuario U2, en el paso 4, no «verá» las modificaciones realizadas por el usuario U1 en la tabla T. Solo las verá después de que U1 haya ejecutado un COMMIT de su transacción.

    En este modo, también conocido como «lectura no repetible», pueden darse, no obstante, las siguientes situaciones:

    1. un usuario U1 inicia una transacción en una tabla T
    2. un usuario U2 inicia una transacción en la misma tabla T
    3. el usuario U2 ejecuta un SELECT para obtener la media de una columna C de las filas de T que cumplen una determinada condición
    4. el usuario U1 modifica (UPDATE) ciertos valores de la columna C de T y los valida (COMMIT)
    5. el usuario U2 repite la misma consulta SELECT que en el punto 3. Descubrirá que la media de la columna C ha cambiado como resultado de las modificaciones realizadas por U1.

    Ahora el usuario U2 solo ve las modificaciones «validadas» por U1. Pero, aunque permanece en la misma transacción, dos operaciones idénticas 3 y 5 dan resultados diferentes. Esta situación se conoce como «lectura no repetible». Es una situación molesta para cualquiera que desee tener una imagen estable de la tabla T.

    Lectura repetible

    En este modo de aislamiento, se garantiza al usuario que obtendrá los mismos resultados en sus lecturas de la base de datos siempre que permanezca en la misma transacción. Trabaja sobre una instantánea en la que nunca se reflejan las modificaciones realizadas por otras transacciones, ni siquiera las validadas. Solo las verá cuando finalice su transacción con un COMMIT o un ROLLBACK.

    Sin embargo, este modo de aislamiento aún no es perfecto. Tras la operación 3 anterior, las filas consultadas por el usuario U2 quedan bloqueadas. Durante la operación 4, el usuario U1 no podrá modificar (UPDATE) los valores de la columna C de estas filas. Sin embargo, sí puede añadir filas (INSERT). Si algunas de las filas añadidas cumplen la condición comprobada en 3, la operación 5 dará un promedio diferente al obtenido en 3, debido a las filas añadidas. A estas filas se las denomina a veces «filas fantasma».

    Para resolver este nuevo problema, debemos cambiar al aislamiento «Serializable».

    Serializable

    En este modo de aislamiento, las transacciones están completamente aisladas unas de otras. Garantiza que el resultado de dos transacciones realizadas simultáneamente será el mismo que si se hubieran realizado una tras otra. Para lograr este resultado, en la operación 4, cuando el usuario U1 quiera añadir líneas que cambiarían el resultado de su SELECT, se le impedirá hacerlo. Un mensaje de error le indicará que la inserción no es posible. Será posible una vez que el usuario U2 haya validado su transacción.

    Los cuatro niveles SQL de aislamiento de transacciones no están disponibles en todos los SGBD. El nivel de aislamiento predeterminado suele ser la lectura confirmada. El nivel de aislamiento deseado para una transacción se puede especificar explícitamente cuando un cliente .NET crea una transacción explícita.

    9.6.2. El sistema de gestión de transacciones de la API

    Una conexión implementa la interfaz IDbConnection presentada en el apartado 9.3.3. Esta interfaz dispone del siguiente método:

    BeginTransaction
    M
    inicia una transacción.

    Este método tiene dos firmas:

    1. IDbTransaction BeginTransaction() : inicia una transacción y devuelve el objeto IDbTransaction para controlarla
    2. IDbTransaction BeginTransaction(IsolationLevel level): también especifica el nivel de aislamiento requerido para la transacción. level toma sus valores de la siguiente enumeración: 
    ReadUncommitted
    la transacción puede leer datos escritos por otra transacción que esta última aún no ha validado; evítese esto
    ReadCommitted
    la transacción no puede leer datos escritos por otra transacción que aún no haya validado. Sin embargo, los datos leídos dos veces seguidas por la transacción pueden cambiar (lecturas no repetibles) porque otra transacción puede haberlos modificado mientras tanto (las líneas leídas no están bloqueadas, solo lo están las líneas actualizadas). Además, otra transacción puede haber añadido líneas (líneas fantasma) que se incluirán en la segunda lectura.
    RepeatableRead
    las líneas leídas por la transacción se bloquean de la misma manera que las líneas actualizadas. Esto impide que otra transacción las modifique. No impide que se añadan filas.
    Serializable
    Las tablas utilizadas por la transacción se bloquean, lo que impide que otra transacción añada nuevas filas. Todo ocurre como si la transacción estuviera sola. Reduce el rendimiento, ya que las transacciones ya no funcionan en paralelo.
    Snapshot
    la transacción opera sobre una copia de los datos realizada en el momento T. Se utiliza cuando la transacción es de solo lectura. Ofrece el mismo resultado que «serializable» evitando su coste.

    Una vez iniciada la transacción, esta es controlada por IDbTransaction, una interfaz con las siguientes propiedades P y métodos M:

using System;
using System.Collections.Generic;
using System.Data.Common;
using Entites;
 
namespace Dao {
    public class DataBaseImpot : IImpotDao {
         // tax brackets
        private TrancheImpot[] tranchesImpot;
        public TrancheImpot[] TranchesImpot { get { return tranchesImpot; } }
 
         // manufacturer
        public DataBaseImpot(string factory, string connectionString, string requête) {
             // factory: the factory of the target SGBD
             // connectionString: connection string to tax bracket base
             // handle any exceptions
            try {
                 // we retrieve a generic connector for the SGBD
                DbProviderFactory connecteur = DbProviderFactories.GetFactory(factory);
                using (DbConnection connexion = connecteur.CreateConnection()) {
                     // connection configuration
                    connexion.ConnectionString = connectionString;
                     // opening connection
                    connexion.Open();
                    // configuration Command 
                    DbCommand sqlCommand = connecteur.CreateCommand();
                    sqlCommand.CommandText = requête;
                    sqlCommand.Connection = connexion;
                     // request execution
                    List<TrancheImpot> listTrancheImpot = new List<TrancheImpot>();
                    using (DbDataReader reader = sqlCommand.ExecuteReader()) {
                        while (reader.Read()) {
                             // a new tax trance is created
                            listTrancheImpot.Add(new TrancheImpot() { Limite = reader.GetDecimal(0), CoeffR = reader.GetDecimal(1), CoeffN = reader.GetDecimal(2) });
                        }
                    }
                     // put the tax brackets in your instance
                    tranchesImpot = listTrancheImpot.ToArray();
                }
            } catch (Exception ex) {
                 // encapsulate the exception in a ImpotException type
                throw new ImpotException("Erreur de lecture des tranches d'impôt", ex) { Code = 101 };
            }
 
        }
    }
}
