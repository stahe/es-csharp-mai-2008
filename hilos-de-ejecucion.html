    10. Hilos de ejecución

    10.1. La clase Thread

    Cuando se inicia una aplicación, esta se ejecuta en un flujo de ejecución denominado subproceso. La clase de .NET que representa un subproceso es System.Threading.Thread y tiene la siguiente definición:

    Fabricantes

    En los siguientes ejemplos, solo utilizaremos los constructores [1,3]. El constructor [1] admite como parámetro un método con la firma [2], es decir, con un parámetro de tipo object y que no devuelve ningún resultado. El constructor [3] acepta como parámetro un método con la firma [4], es decir, que no tiene ningún parámetro y no devuelve ningún resultado.

    Propiedades

    Algunas propiedades útiles:

    • Thread CurrentThread : propiedad estática que proporciona una referencia al hilo en el que se encuentra el código que solicita esta propiedad
    • string Name: nombre del hilo
    • bool IsAlive: indica si el hilo se está ejecutando o no.

    Métodos

    Los métodos más utilizados son:

    • Start(), Start(object obj): inicia la ejecución asíncrona del hilo, posiblemente pasándole información en un objeto.
    • Abort(), Abort(object obj): para terminar un hilo de forma forzada
    • Join(): el hilo T1 que ejecuta T2.Join queda bloqueado hasta que finalice T2. Existen variantes para finalizar la espera tras un tiempo determinado.
    • Sleep(int n): método estático; el hilo que ejecuta el método se suspende durante n milisegundos. A continuación, pierde el procesador, que se cede a otro hilo.

    Echemos un vistazo a una primera aplicación que demuestra la existencia de un hilo principal de ejecución, aquel en el que se encuentra la función Main de una clase:

    10.2. Creación de subprocesos de ejecución

    Es posible tener aplicaciones en las que fragmentos de código se ejecuten «simultáneamente» en diferentes subprocesos de ejecución. Cuando decimos que los subprocesos se ejecutan simultáneamente, a menudo se trata de un término impropio. Si la máquina solo tiene un procesador, como sigue siendo habitual, los subprocesos comparten este procesador: cada uno tiene acceso a él, por turnos, durante un breve periodo de tiempo (unos pocos milisegundos). Esto da la impresión de una ejecución paralela. El tiempo asignado a un hilo depende de varios factores, incluida su prioridad, que tiene un valor por defecto pero que también se puede establecer mediante programación. Cuando un hilo tiene el procesador, lo utiliza normalmente durante todo el tiempo asignado. Sin embargo, puede liberarlo antes de tiempo:

    • esperando un evento (Wait, Join)
    • poniéndose en estado de suspensión durante un periodo de tiempo determinado (Sleep)
    1. Un hilo T es creado inicialmente por uno de los fabricantes mencionados anteriormente, por ejemplo: 
    Thread thread=new Thread(Start);

    donde Start es un método con una de las dos firmas siguientes:

    void Start();
void Start(object obj);

    Crear un subproceso no lo inicia.

    1. El hilo T se inicia mediante T.Start(): el método Start pasado al constructor de T será ejecutado a continuación por el hilo T. El programa que ejecuta T.Start() no espera a que la tarea T termine: pasa inmediatamente a la siguiente instrucción. Esto significa que hay dos tareas ejecutándose en paralelo. En muchos casos, necesitan poder comunicarse entre sí para realizar un seguimiento del progreso de su trabajo conjunto. Este es el problema de la sincronización de hilos.
    2. Una vez iniciado, el hilo T se ejecuta de forma autónoma. Se detendrá cuando el Start que ejecuta haya terminado su trabajo.
    3. Se puede forzar la terminación del hilo T:
      1. T.Abort() solicita al hilo T que termine.
    4. También se puede esperar a que finalice su ejecución mediante T.Join(). Se trata de una instrucción de bloqueo: el programa que la ejecuta queda bloqueado hasta que la tarea T haya completado su trabajo. Este es un método de sincronización.

    Echemos un vistazo al siguiente programa:

    
using System;
using System.Threading;
 
namespace Chap8 {
    class Program {
        public static void Main() {
             // init Current thread
            Thread main = Thread.CurrentThread;
             // name the Thread
            main.Name = "Main";
 
             // creation of execution threads
            Thread[] tâches = new Thread[5];
            for (int i = 0; i < tâches.Length; i++) {
                 // create thread i
                tâches[i] = new Thread(Affiche);
                 // set the thread name
                tâches[i].Name =  i.ToString();
                 // start execution of thread i
                tâches[i].Start();
            }
 
             // end of hand
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}",main.Name,DateTime.Now);
        }
 
        public static void Affiche() {
             // display start of execution
            Console.WriteLine("Début d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}",Thread.CurrentThread.Name,DateTime.Now);
             // sleep for 1 s
            Thread.Sleep(1000);
             // display end of run
            Console.WriteLine("Fin d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}", Thread.CurrentThread.Name, DateTime.Now);
        }
    }
}

    10.3. Las ventajas de los hilos

    Ahora que hemos destacado la existencia de un subproceso predeterminado, el que ejecuta Main, y sabemos cómo crear otros nuevos, veamos qué significan los subprocesos para nosotros y por qué los introducimos aquí. Hay un tipo de aplicación que se presta muy bien al uso de subprocesos, y son las aplicaciones cliente-servidor de Internet. Las presentaremos en el siguiente capítulo. En una aplicación cliente-servidor de Internet, un servidor en la máquina S1 responde a las solicitudes de los clientes en máquinas remotas C1, C2, ..., Cn.

    Todos los días utilizamos aplicaciones de Internet que se corresponden con este diagrama: servicios web, correo electrónico, consulta de foros, transferencia de archivos... En el diagrama anterior, el servidor S1 debe atender a los clientes Ci simultáneamente. Si tomamos el ejemplo de un servidor FTP (Protocolo de Transferencia de Archivos) que entrega archivos a sus clientes, sabemos que una transferencia de archivos puede tardar a veces varios minutos. Por supuesto, es impensable que un cliente monopolice el servidor durante todo ese tiempo. Lo que se suele hacer es que el servidor cree tantos subprocesos de ejecución como clientes haya. Cada subproceso se encarga entonces de atender a un cliente concreto. Como el procesador se comparte cíclicamente entre todos los subprocesos activos de la máquina, el servidor dedica un poco de tiempo a cada cliente, garantizando así un servicio simultáneo.

    En la práctica, el servidor utiliza un grupo de subprocesos con un número limitado de subprocesos, 50 por ejemplo. Al cliente número 51 se le pide entonces que espere.

    10.4. Intercambio de información entre subprocesos

    En los ejemplos anteriores, un subproceso se inicializaba de la siguiente manera:

    Thread t=new Thread(Run);

    donde Run era un método con la siguiente firma:

    void Run();

    También es posible utilizar la siguiente firma:

    void Run(object obj);

    Esto permite transmitir información al subproceso iniciado. Por ejemplo,

    t.Start(obj1);

    iniciará el t, que a continuación ejecutará el Run asociado a él por diseño, pasándole el parámetro efectivo obj1. He aquí un ejemplo:

    
using System;
using System.Threading;

namespace Chap8 {
    class Program4 {
        public static void Main() {
             // init Current thread
            Thread main = Thread.CurrentThread;
             // name the Thread
            main.Name = "Main";
 
             // creation of execution threads
            Thread[] tâches = new Thread[5];
            Data[] data = new Data[5];
            for (int i = 0; i < tâches.Length; i++) {
                 // create thread i
                tâches[i] = new Thread(Sleep);
                 // set the thread name
                tâches[i].Name = i.ToString();
                 // start execution of thread i
                tâches[i].Start(data[i] = new Data { Début = DateTime.Now, Durée = i+1 });
            }
             // we wait for all threads
            for (int i = 0; i < tâches.Length; i++) {
                 // wait for thread i to finish execution
                tâches[i].Join();
                 // result display
                Console.WriteLine("Thread {0} terminé : début {1:hh:mm:ss}, durée programmée {2} s, fin {3:hh:mm:ss}, durée effective {4}",
                    tâches[i].Name,data[i].Début,data[i].Durée,data[i].Fin,(data[i].Fin-data[i].Début));
            }        
             // end of hand
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}", main.Name, DateTime.Now);
        }
 
        public static void Sleep(object infos) {
             // parameter is retrieved
            Data data = (Data)infos;
             // sleep mode for Duration
            Thread.Sleep(data.Durée*1000);
             // end of execution
            data.Fin = DateTime.Now;
        }
    }
 
    internal class Data {
         // miscellaneous information
        public DateTime Début { get; set; }
        public int Durée { get; set; }
        public DateTime Fin { get; set; }
    }
}

    10.5. Acceso competitivo a recursos compartidos

    10.5.1. Acceso concurrente no sincronizado

    En el apartado sobre el intercambio de información entre subprocesos, la información se intercambiaba solo entre dos subprocesos y en momentos muy concretos. Se trataba de un clásico paso de parámetros. En otros casos, la información es compartida por varios subprocesos, que pueden querer leerla o actualizarla al mismo tiempo. Esto plantea el problema de la integridad de la información. Supongamos que la información compartida es una estructura S con varios elementos de información I1, I2, ... In.

    • Un subproceso T1 comienza a actualizar la estructura S: modifica el campo I1 y es interrumpido antes de completar toda la actualización de la estructura S
    • un subproceso T2 que recupera el procesador lee entonces la estructura S para tomar decisiones. Lee una estructura en un estado inestable: algunos campos están actualizados, otros no.

    A esta situación la denominamos «acceso a un recurso compartido», en este caso la estructura S, y a menudo resulta bastante complicado gestionarla. Veamos el siguiente ejemplo para ilustrar los problemas que pueden surgir:

    • una aplicación generará n subprocesos, donde n se pasa como parámetro
    • el recurso compartido es un contador que debe ser incrementado por cada subproceso generado
    • al final de la aplicación, se muestra el valor del contador. Por lo tanto, debemos hallar n.

    El programa es el siguiente:

    
using System;
using System.Threading;
 
namespace Chap8 {
    class Program {
 
         // class variables
         static int cptrThreads     = 0; // thread counter
 
         //hand
        public static void Main(string[] args) {
             // instructions for use
            const string syntaxe = "pg nbThreads";
            const int nbMaxThreads = 100;
 
             // verification no. of arguments
            if (args.Length != 1) {
                 // error
                Console.WriteLine(syntaxe);
                 // stop
                Environment.Exit(1);
            }
             // argument quality check
            int nbThreads = 0;
            bool erreur = false;
            try {
                nbThreads = int.Parse(args[0]);
                if (nbThreads < 1 || nbThreads > nbMaxThreads)
                    erreur = true;
            } catch {
                 // error
                erreur = true;
            }
             // mistake?
            if (erreur) {
                 // error
                Console.Error.WriteLine("Nombre de threads incorrect (entre 1 et 100)");
                 // end
                Environment.Exit(2);
            }
             // thread creation and generation
            Thread[] threads = new Thread[nbThreads];
            for (int i = 0; i < nbThreads; i++) {
                 // creation
                threads[i] = new Thread(Incrémente);
                 // naming
                threads[i].Name = "" + i;
                 // launch
                threads[i].Start();
            }//for
             // waiting for threads to finish
            for (int i = 0; i < nbThreads; i++) {
                threads[i].Join();
            }
             // counter display
            Console.WriteLine("Nombre de threads générés : " + cptrThreads);
        }
 
        public static void Incrémente() {
             // increases thread counter
             // meter reading
            int valeur = cptrThreads;
             // follow-up
            Console.WriteLine("A {0:hh:mm:ss}, le thread {1}  a lu la valeur du compteur : {2}", DateTime.Now, Thread.CurrentThread.Name, cptrThreads);
             // waiting
            Thread.Sleep(1000);
             // counter incrementation
            cptrThreads = valeur + 1;
             // follow-up
            Console.WriteLine("A {0:hh:mm:ss}, le thread {1}  a écrit la valeur du compteur : {2}", DateTime.Now, Thread.CurrentThread.Name, cptrThreads);
        }

    10.5.3. La clase Mutex

    La clase System.Threading.Mutex también se puede utilizar para delimitar secciones críticas. Se diferencia del bloqueo en cuanto a la visibilidad:

    • la cláusula lock sincroniza subprocesos de la misma aplicación
    • la clase Mutex permite sincronizar subprocesos de diferentes aplicaciones.

    Utilizaremos el siguiente constructor y los siguientes métodos:

    public Mutex()
    crea un Mutex M
    public bool WaitOne()
    El subproceso T1 que ejecuta M.WaitOne() solicita la propiedad del objeto de sincronización M. Si ningún subproceso tiene el Mutex M (como ocurría al principio), se «concede» al subproceso T1 que lo ha solicitado. Si, poco después, un hilo T2 realiza la misma operación, quedará bloqueado. Esto se debe a que un Mutex solo puede pertenecer a un hilo. Se desbloqueará cuando el hilo T1 libere el Mutex M que mantiene. Por lo tanto, varios hilos pueden quedar bloqueados mientras esperan el Mutex M.
    public void ReleaseMutex()
    El hilo T1 que ejecuta M.ReleaseMutex() cede la propiedad del mutex M. Cuando el hilo T1 pierde el procesador, el sistema puede asignárselo a uno de los hilos que esperan el mutex M. Solo uno lo obtendrá por turnos, mientras que los demás que esperan M permanecerán bloqueados

    Un mutex M gestiona el acceso a un recurso compartido R. Un hilo solicita el recurso R mediante M.WaitOne() y lo libera con M.ReleaseMutex().     10.5.4. La clase AutoResetEvent

    Un objeto AutoResetEvent es una barrera que solo permite el paso de un subproceso a la vez, al igual que las dos herramientas anteriores, lock y Mutex. Creamos un objeto AutoResetEvent de la siguiente manera:

    AutoResetEvent barrière=new AutoresetEvent(bool état);

    El valor booleano état indica si la barrera está cerrada (false) o abierta (true). Un subproceso que desee atravesar la barrera lo indicará de la siguiente manera:

    barrière.WaitOne();
    • si la barrera está abierta, el hilo la atraviesa y la barrera se cierra tras él. Si había varios hilos esperando, podemos estar seguros de que solo uno pasará.

    barrière.Set();

    barrière.Reset();

    10.6. Acceso competitivo a múltiples recursos compartidos

    10.6.1. Un ejemplo

    En nuestros ejemplos anteriores, un único recurso era compartido por los diferentes subprocesos. La situación puede complicarse si hay varios recursos y estos dependen unos de otros. Esto puede dar lugar a una situación de interbloqueo. Esta situación, también conocida como interbloqueo, se produce cuando dos subprocesos se esperan mutuamente. Consideremos las siguientes acciones que se suceden en el tiempo:

    • un subproceso T1 obtiene la propiedad de un mutex M1 para acceder a un recurso compartido R1
    • un subproceso T2 obtiene la propiedad de un mutex M2 para acceder a un recurso compartido R2
    • el subproceso T1 solicita el mutex M2. Queda bloqueado.
    • el subproceso T2 solicita el mutex M1. Queda bloqueado.

    En este caso, los subprocesos T1 y T2 se esperan mutuamente. Esta situación se produce cuando los subprocesos necesitan dos recursos compartidos: el recurso R1 controlado por el mutex M1 y el recurso R2 controlado por el mutex M2. Una posible solución es solicitar ambos recursos al mismo tiempo, utilizando un único mutex M. Pero esto no siempre es posible, por ejemplo, si implica una movilización de un recurso costoso que requiere mucho tiempo. Otra solución es que un hilo que tiene M1 y no puede obtener M2 libere M1 para evitar el bloqueo.

    1. Tenemos una matriz en la que algunos subprocesos depositan datos (escritores) y otros los leen (lectores).
    2. Los escritores son iguales pero exclusivos: solo un escritor a la vez puede introducir datos en la tabla.
    3. Los lectores son iguales pero exclusivos: solo un lector a la vez puede leer los datos depositados en la tabla.
    4. Un lector solo puede leer los datos de la tabla una vez que un escritor haya depositado datos en ella, y un escritor solo puede depositar nuevos datos en la tabla una vez que los datos que contiene hayan sido leídos por un lector.

    Se pueden distinguir dos recursos compartidos:

    • la pizarra de escritura: solo un escritor a la vez puede tener acceso a ella.
    • el tablero de visualización de solo lectura: solo un lector a la vez puede acceder a él.

    y un orden de uso de estos recursos:

    • un lector siempre debe venir después de un escritor.
    • Un escritor siempre debe ir después de un lector, excepto la primera vez.

    El acceso a estos dos recursos se puede controlar con dos barreras de tipo AutoResetEvent:

    • la barrera peutEcrire controlará el acceso de los escritores al tablero.
    • La barrera peutLire controlará el acceso de los lectores al tablero.
    • La barrera peutEcrire se creará inicialmente abierta, permitiendo el paso al primer escritor y bloqueando a todos los demás.
    • La barrera peutLire se creará inicialmente cerrada, bloqueando a todos los lectores.
    • Cuando un escritor haya terminado su trabajo, abrirá la puerta «peutLire» para dejar entrar a un lector.
    • Cuando un lector haya terminado su trabajo, abrirá la puerta «peutEcrire» para dejar entrar a un escritor.

    10.6.2. La clase Monitor

    En el ejemplo anterior:

    • para un recurso dado, los subprocesos son iguales.

    La analogía es con un establecimiento que atiende al público en mostradores, donde cada mostrador está especializado. Cuando llegan los clientes, cogen un ticket del dispensador de tickets para el mostrador X y luego se sientan. Cada vez, el altavoz le despierta anunciando que se ha llamado al número Y para que acuda al mostrador X.     cada hilo comprueba si es el elegido. Si lo es, cruza la barrera. Si no, vuelve a la espera.

    La clase Monitor se utiliza para implementar este escenario.

    A continuación describimos una construcción estándar (patrón), propuesta en el capítulo «Threading» del libro C# 3.0 al que se hace referencia en la introducción de este documento, capaz de resolver problemas de barrera con condiciones de entrada.

    • En primer lugar, los subprocesos que comparten un recurso (el contador, etc.) acceden a él a través de un objeto que llamaremos «token». Para abrir la puerta que conduce al contador, es necesario disponer del token, y solo hay un token. Por lo tanto, los subprocesos deben pasarse el token entre sí. 
    object jeton=new object();
    • Para llegar al contador, los subprocesos solicitan primero el : 
    Monitor.Enter(jeton);

    Si el token está libre, se le asigna al hilo que ejecutó la operación anterior; de lo contrario, el hilo queda en espera del token.

    • Si el acceso al contador no está ordenado, es decir, si no importa quién entre, la operación anterior es suficiente. El hilo con el token va al contador. Si el acceso está ordenado, el hilo con el token comprueba que cumple la condición para ir al contador: 
    while (! jeNeSuisPasCeluiQuiEstAttendu) {Monitor.Wait(jeton);}

    Si el hilo no es el esperado en el mostrador, cede su turno devolviendo el token. Entra en un estado bloqueado. Se reactivará tan pronto como el token vuelva a estar disponible. Entonces volverá a comprobar si cumple la condición para ir al mostrador. La operación Monitor.Wait(token) que libera el token solo se puede realizar si el hilo es propietario del token. Si no es así, se lanza una excepción.

    • El hilo que comprueba la condición para ir al contador se dirige allí:
    1. // trabajo del contador
    2. ....

    10.7. Grupos de subprocesos

    Hasta ahora, para gestionar :

    • los creábamos mediante Thread T = new Thread(...)
    • y luego los ejecutábamos con T.Start()

    En el capítulo «Bases de datos» vimos que con algunos SGBD era posible disponer de grupos de conexiones abiertas:

    • se abren n conexiones al iniciar el grupo
    • cuando un hilo solicita una conexión, se le asigna una de las conexiones abiertas del grupo
    • cuando el hilo cierra la conexión, esta no se cierra, sino que se devuelve al grupo

    El uso de un grupo de conexiones es transparente para el código. La ventaja radica en la mejora del rendimiento: abrir una conexión es costoso. Aquí, 10 conexiones abiertas pueden atender cientos de solicitudes.

    Existe un sistema similar para los subprocesos:

    • Se crean un mínimo de subprocesos al iniciar el grupo. El valor de min se establece mediante ThreadPool.SetMinThreads(min1, min2). Un grupo de subprocesos se puede utilizar para ejecutar tareas asíncronas bloqueantes o no bloqueantes. El primer parámetro, min1, establece el número de subprocesos bloqueantes; el segundo, min2, el número de subprocesos asíncronos. Los valores actuales de estas dos variables se pueden obtener mediante ThreadPool.GetMinThreads(out min1, out min2).
    • Si este número no es suficiente, el grupo creará otros subprocesos para responder a las solicitudes hasta el límite de subprocesos máximos. El valor de max se establece mediante ThreadPool.SetMaxThreads(max1, max2). Ambos parámetros tienen el mismo significado que en SetMinThreads. Los valores actuales de estas dos variables se pueden obtener mediante ThreadPool.GetMaxThreads(out max1, out max2). Cuando se alcanza el número de subprocesos max1, las solicitudes de subprocesos para tareas de bloqueo se pondrán en cola a la espera de un subproceso libre en el grupo.

    Un grupo de subprocesos ofrece una serie de ventajas:

    • al igual que con el grupo de conexiones, ahorramos tiempo en la creación de subprocesos: 10 subprocesos pueden atender cientos de solicitudes.
    • protegemos la aplicación: al establecer un número máximo de subprocesos, evitamos saturar la aplicación con demasiadas solicitudes. Estas se colocarán en la cola de archivos.

    Para asignar una tarea a un hilo del grupo, utilice uno de estos dos métodos:

    1. ThreadPool.QueueWorkItem(WaitCallBack)
    2. ThreadPool.QueueWorkItem(WaitCallBack, object)

    donde WaitCallBack es cualquier método con la firma void WaitCallBack(object). El método 1 solicita a un subproceso que ejecute el método WaitCallBack sin pasar ningún parámetro. El método 2 hace lo mismo, pero pasa un parámetro de tipo object a WaitCallBack.

    10.8. La clase BackgroundWorker

    10.8.1. Ejemplo 1

    La clase BackgroundWorker pertenece al espacio de nombres [System.ComponentModel]. Se utiliza de la misma manera que un subproceso, pero tiene algunas características especiales que pueden hacerla más interesante que la clase [Thread] en ciertos casos:

    • emite los siguientes eventos:
    • DoWork: un subproceso ha solicitado la ejecución de BackgroundWorker
    • ProgressChanged: el objeto BackgroundWorker ha ejecutado ReportProgress. Se utiliza para indicar el porcentaje de finalización.
    • RunWorkerCompleted: el objeto BackgroundWorker ha completado su trabajo. Puede haberlo completado normalmente, o con una cancelación o una excepción.

    Estos eventos hacen que el BackgroundWorker resulte útil en interfaces gráficas: una tarea que requiere mucho tiempo se confiará a un BackgroundWorker, que podrá informar de su progreso mediante el evento ProgressChanged y de su finalización mediante el evento RunWorkerCompleted. El trabajo que debe realizar el BackgroundWorker se llevará a cabo mediante un método asociado a DoWork.

    • Es posible solicitar su cancelación. En una interfaz gráfica, el usuario puede cancelar una tarea larga.
    • Los objetos BackgroundWorker pertenecen a un grupo y se reciclan según sea necesario. Una aplicación que necesite un BackgroundWorker lo obtendrá del grupo, que le proporcionará un subproceso existente pero sin usar. Reciclar subprocesos de esta manera, en lugar de crear uno nuevo cada vez, mejora el rendimiento.

    10.9. Datos locales del hilo

    10.9.1. El principio

    Consideremos una aplicación de tres capas:

    Supongamos que la aplicación es multiusuario, por ejemplo, una aplicación web. Cada usuario es atendido por un hilo dedicado. La vida del hilo es la siguiente:

    1. el hilo se crea o se solicita a un grupo de hilos para satisfacer una solicitud del usuario
    2. si esta solicitud requiere datos, el hilo ejecutará un método de la capa [ui], que llamará a un método de la capa [metier], el cual, a su vez, llamará a un método de la capa [dao].
    3. el hilo devuelve la respuesta al usuario. A continuación, desaparece o se recicla en un grupo de hilos.

    En la operación 2, puede ser interesante que el hilo tenga sus propios datos, es decir, que no los comparta con otros hilos. Estos datos podrían, por ejemplo, pertenecer al usuario concreto al que el hilo está prestando servicio. Estos datos podrían utilizarse entonces en las distintas capas [ui, metier, dao].

    La clase Thread permite este escenario gracias a una especie de diccionario privado cuyas claves serían de tipo LocalDataStoreSlot:

    crea una entrada en el diccionario privado del hilo para el nombre de la clave.
    asocia el dato de valor a la clave «name» del diccionario privado del hilo
    recupera el valor asociado al nombre del diccionario privado del hilo

    Un modelo de uso podría ser el siguiente:

    • para crear un par (clave, valor) asociado al hilo actual: 
    Thread.SetData(Thread.GetNamedDataSlot("clé"),valeur);
    • para recuperar el valor asociado a la clave: 
    Thread.GetData(Thread.GetNamedDataSlot("clé"));

    • colocar solo operaciones básicas en la capa [dao]: InsertArticle, DeleteArticle, UpdateArticle, SelectArticle, SelectArticles
    • trasladar a la capa [business] la actualización simultánea de varios artículos. Estas utilizarían las operaciones elementales de la capa [dao].

    • la transacción debe ser iniciada por la capa [metier] antes de que esta llame a los métodos de la capa [dao]
    • los métodos de la capa [dao] deben ser conscientes de la existencia de la transacción para poder participar en ella si existe
    • la transacción debe ser terminada por la capa [business].

    Para garantizar que los métodos de la capa [dao] sean conscientes de la existencia de cualquier transacción en curso, podríamos añadir la transacción como parámetro a cada método de la capa [dao]. Este parámetro aparecerá entonces en la firma de los métodos de la interfaz, vinculándola a una fuente de datos específica: la base de datos. Los datos locales del hilo nos proporcionan una solución más elegante: la capa [business] colocará la transacción en los datos locales del hilo, y la capa [dao] la recuperará de allí. No es necesario cambiar la firma de los métodos de la capa [dao].

    Implementación de la capa [metier]

    La implementación de la interfaz IMetier será la siguiente:

    
using System.Collections.Generic;
using System.Data;
using System.Data.SqlServerCe;
using System.Threading;
 
namespace Chap8 {
    public class Metier : IMetier {
         // layer [dao]
        public IDao Dao { get; set; }
         // connecting chain
        public string ConnectionString { get; set; }
 
        // insert an array of articles inside a transaction
        public void InsertArticlesInTransaction(Article[] articles) {
            // create the connection to the
            using (SqlCeConnection connexion = new SqlCeConnection(ConnectionString)) {
                 // opening connection
                connexion.Open();
                 // transaction
                SqlCeTransaction transaction = null;
                try {
                     // start of transaction
                    transaction = connexion.BeginTransaction(IsolationLevel.ReadCommitted);
                    // register the transaction in the thread
                    Thread.SetData(Thread.GetNamedDataSlot("transaction"), transaction);
                     // articles insertion
                    foreach (Article article in articles) {
                        Dao.InsertArticle(article);
                    }
                    // validate the transaction
                    transaction.Commit();
                } catch {
                    // we undo the transaction
                    if (transaction != null)
                        transaction.Rollback();
                }
            }
        }
 
        // insertion of an array of articles without transaction
        public void InsertArticlesOutOfTransaction(Article[] articles) {
             // articles insertion
            foreach (Article article in articles) {
                Dao.InsertArticle(article);
            }
        }
 
         // articles list
        public List<Article> GetAllArticles() {
            return Dao.GetAllArticles();
        }
         // delete all articles
        public void DeleteAllArticles() {
            Dao.DeleteAllArticles();
        }
    }
}

    La clase tiene las siguientes propiedades:

    • línea 9: una referencia a la capa [dao]
    • línea 11: la cadena de conexión utilizada para conectarse a la base de datos de artículos

    Solo comentamos el método InsertArticlesInTransaction, que por sí solo presenta dificultades:

    • línea 16: se crea una conexión con la base de datos
    • línea 18: ahora se abre
    • línea 23: se crea una transacción
    • línea 25: se guarda en los datos locales del hilo, asociados a la clave «transaction»
    • líneas 27-29: se llama al método de inserción de la unidad de la capa [dao] para cada elemento que se va a insertar
    • líneas 21 y 32: toda la inserción de la matriz se controla mediante un try / catch
    • línea 31: si se llega a este punto, no se ha producido ninguna excepción. A continuación, se valida la transacción.
    • líneas 34-35: se ha producido una excepción, la transacción se deshace
    • línea 37: se sale de la cláusula mediante. La conexión abierta en la línea 18 se cierra automáticamente.

    Implementación de la capa [dao]

    La implementación de la interfaz Dao IDao será la siguiente:

    
using System.Collections.Generic;
using System.Data;
using System.Data.SqlServerCe;
using System.Threading;
 
namespace Chap8 {
    public class Dao : IDao {
         // connecting chain
        public string ConnectionString { get; set; }
         // requests
        public string InsertText { get; set; }
        public string DeleteAllText { get; set; }
        public string GetAllText { get; set; }
 
         // interface implementation

         // article insertion
        public int InsertArticle(Article article) {
            // is there a transaction in progress?
            SqlCeTransaction transaction = Thread.GetData(Thread.GetNamedDataSlot("transaction")) as SqlCeTransaction;
            // retrieve or create connection
            SqlCeConnection connexion = null;
            if (transaction != null) {
                 // recover connection
                connexion = transaction.Connection as SqlCeConnection;
            } else {
                 // create it
                connexion = new SqlCeConnection(ConnectionString);
                connexion.Open();
            }
            try {
                 // preparation of insertion order
                SqlCeCommand sqlCommand = new SqlCeCommand();
                sqlCommand.Transaction = transaction;
                sqlCommand.Connection = connexion;
                sqlCommand.CommandText = InsertText;
                sqlCommand.Parameters.Add("@nom", SqlDbType.NVarChar, 30);
                sqlCommand.Parameters.Add("@prix", SqlDbType.Money);
                sqlCommand.Parameters.Add("@sa", SqlDbType.Int);
                sqlCommand.Parameters.Add("@sm", SqlDbType.Int);
                sqlCommand.Parameters["@nom"].Value = article.Nom;
                sqlCommand.Parameters["@prix"].Value = article.Prix;
                sqlCommand.Parameters["@sa"].Value = article.StockActuel;
                sqlCommand.Parameters["@sm"].Value = article.StockMinimum;
                 // execution
                return sqlCommand.ExecuteNonQuery();
            } finally {
                // if you were not in a transaction, you close the connection
                if (transaction == null) {
                    connexion.Close();
                }
            }
        }
 
         // articles list
        public List<Article> GetAllArticles() {
...
        }
 
         // deletion of articles
        public void DeleteAllArticles() {
...
        }
    }
}

    10.9.3. Conclusión

    El ejemplo anterior mostraba las ventajas de los datos locales del hilo para la gestión de transacciones. No debe reproducirse tal cual. Los marcos de trabajo como Spring, Nhibernate, etc., utilizan esta técnica, pero la hacen aún más transparente: la capa [metier] puede utilizar transacciones sin que la capa [dao] tenga que saberlo. No hay transacciones en el código de la capa [dao]. Esto se consigue utilizando una técnica de proxy llamada AOP (programación orientada a aspectos). Una vez más, le recomendamos encarecidamente que utilice estos marcos de trabajo.
