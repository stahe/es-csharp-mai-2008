    La experiencia práctica ha demostrado que aislar estos diferentes procesos en clases separadas mejora la facilidad de mantenimiento de las aplicaciones. La arquitectura de una aplicación estructurada de esta manera es la siguiente:

    Esta arquitectura se denomina «arquitectura de tres capas». El término «tres capas» suele referirse a una arquitectura en la que cada capa se encuentra en una máquina diferente. Cuando las capas se encuentran en la misma máquina, la arquitectura pasa a denominarse «arquitectura de tres capas».

    • La capa [de negocio] contiene las reglas de negocio de la aplicación. En el caso de nuestra aplicación de cálculo de impuestos, se trata de las reglas utilizadas para calcular los impuestos de un contribuyente. Esta capa necesita datos para funcionar:
    • tramos impositivos, que cambian cada año
    • el número de hijos, el estado civil y el salario anual del contribuyente

    En el diagrama anterior, los datos pueden proceder de dos fuentes:

    • la capa de acceso a datos o [dao] (DAO = Objeto de Acceso a Datos) para los datos ya almacenados en archivos o bases de datos. Este podría ser el caso de los tramos impositivos, tal y como se hacía en la versión anterior de la aplicación.
    • la capa de interfaz de usuario o [ui] (UI = Interfaz de usuario) para los datos introducidos por el usuario o mostrados al usuario. Este podría ser el caso aquí del número de hijos, el estado civil y el salario anual del contribuyente
    • en general, la capa [dao] gestiona el acceso a datos persistentes (archivos, bases de datos) o no persistentes (red, sensores, etc.).
    • La capa [ui] gestiona las interacciones con el usuario, si las hay.
    • Las tres capas se independizan mediante el uso de interfaces.

    Vamos a tomar la aplicación [Impots] que ya hemos estudiado varias veces y le daremos una arquitectura de tres capas. Para ello, estudiaremos las capas [ui, metier, dao] una tras otra, empezando por la capa [dao], que se encarga de los datos persistentes.

    En primer lugar, debemos definir las interfaces de las distintas capas de la aplicación [Impots].

    6.2. Interfaces de la aplicación [Impots]

    Recuerda que una interfaz define un conjunto de firmas de métodos. Las clases que implementan la interfaz dan contenido a estos métodos.

    Volvamos a la arquitectura de tres capas de nuestra aplicación:

    En este tipo de arquitectura, suele ser el usuario quien toma la iniciativa. Realiza una solicitud en [1] y recibe una respuesta en [8]. Esto se conoce como el ciclo solicitud-respuesta. Tomemos como ejemplo el cálculo de los impuestos de un contribuyente. Esto requerirá varios pasos:

    1. la capa [ui] deberá preguntar al usuario por el número de hijos, su estado civil y su salario anual. Esta es la operación [1] mencionada anteriormente.
    2. Una vez hecho esto, la capa [ui] pedirá a la capa de negocio que calcule el impuesto. Para ello, transmitirá los datos que ha recibido del usuario. Esta es la operación [2].
    3. La capa [metier] necesita cierta información para llevar a cabo su trabajo: los tramos impositivos. Solicitará esta información a la capa [dao] con la ruta [3, 4, 5, 6]. [3] es la solicitud inicial y [6] la respuesta a dicha solicitud.
    4. Con todos los datos que necesita, la capa [metier] calcula el impuesto.
    5. La capa [metier] ya puede responder a la solicitud realizada por la capa [ui] en (b). Esta es la ruta [7].
    6. La capa [ui] formateará estos resultados y los presentará al usuario. Esta es la ruta [8].
    7. Podríamos imaginar que el usuario realiza simulaciones de impuestos y desea guardarlas. Para ello, utilizaría la ruta [1-8].

    Esta descripción muestra que una capa utilizará los recursos de la capa situada a su derecha, pero nunca los de la capa situada a su izquierda. Consideremos dos capas contiguas:

    La capa [A] realiza solicitudes a la capa [B]. En los casos más sencillos, una capa se implementa mediante una sola clase. Una aplicación evoluciona con el tiempo. Por lo tanto, la capa [B] puede tener diferentes clases de implementación [B1, B2, ...]. Si la capa [B] es la capa [dao], puede tener una primera implementación [B1] que recupere datos de un archivo. Unos años más tarde, es posible que quieras guardar los datos en una base de datos. Entonces creamos una segunda clase de implementación [B2]. Si, en la aplicación inicial, la capa [A] trabajaba directamente con la clase [B1], nos vemos obligados a reescribir parcialmente el código de la capa [A]. Por ejemplo, supongamos que la capa [A] se ha escrito de la siguiente manera:

    1
2
3
    B1 b1=new B1(...);
..
b1.getData(...);
    • línea 1: se crea una instancia de la clase [B1]
    • línea 3: se solicitan datos a esta instancia

    Si suponemos que la nueva clase de implementación [B2] utiliza métodos con la misma firma que los de la clase [B1], tendremos que cambiar todos los [B1] por [B2]. Este es un caso muy favorable, y bastante improbable si no se ha prestado atención a estas firmas de métodos. En la práctica, las clases [B1] y [B2] a menudo no tienen las mismas firmas de método, por lo que gran parte de la capa [A] tiene que reescribirse por completo.

    Esto se puede mejorar creando una interfaz entre las capas [A] y [B]. Esto significa fijar en una interfaz las firmas de los métodos que la capa [B] presenta a la capa [A]. El diagrama anterior se convierte entonces en el siguiente:

    La capa [A] ya no se dirige directamente a la capa [B], sino a su interfaz [IB]. Por lo tanto, en el código de la capa [A], la clase de implementación [Bi] de la capa [B] solo aparece una vez, cuando se implementa la interfaz [IB]. Una vez hecho esto, es la interfaz [IB] y no su clase de implementación la que se utiliza en el código. El código anterior queda así:

    1
2
3
    IB ib=new B1(...);
..
ib.getData(...);
    • línea 1: se crea una instancia [ib] que implementa la interfaz [IB] mediante la instanciación de la clase [B1]
    • línea 3: se solicitan datos a la instancia [ib]

    Ahora bien, si sustituimos la implementación [B1] de la capa [B] por una implementación [B2], y ambas implementaciones respetan la misma interfaz [IB], entonces solo es necesario modificar la línea 1 de la capa [A] y ninguna otra. Esto supone una gran ventaja y, por sí solo, justifica el uso sistemático de interfaces entre dos capas.

    Podemos ir aún más lejos y hacer que la capa [A] sea totalmente independiente de la capa [B]. En el código anterior, la línea 1 es problemática porque hace referencia a la clase [B1]. Lo ideal sería que la capa [A] tuviera una implementación de la interfaz [IB] sin tener que nombrar una clase. Esto sería coherente con nuestro diagrama anterior. Podemos ver que la capa [A] se dirige a la interfaz [IB], y no vemos por qué necesitaría conocer el nombre de la clase que implementa esta interfaz. Este detalle no tiene ninguna utilidad para la capa [A].

    El marco Spring (http://www.springframework.org) logra esto. La arquitectura anterior evoluciona de la siguiente manera:

    La capa transversal [Spring] permitirá que una capa obtenga una referencia a la capa situada a su derecha mediante la configuración, sin necesidad de conocer el nombre de la clase de implementación de dicha capa. Este nombre figurará en los archivos de configuración y no en el código C#. El código C# para la capa [A] adopta entonces la siguiente forma:

    1
2
3
    IB ib; // initialisé par Spring
..
ib.getData(...);
    • línea 1: una instancia [ib] que implementa la interfaz [IB] de la capa [B]. Esta instancia es creada por Spring a partir de la información que se encuentra en un archivo de configuración. Spring creará:
      • la instancia [b] que implementa la capa [B]
      • la instancia [a] que implementa la capa [A]. Esta instancia se inicializará. El campo [ib] anterior se establecerá en la referencia [b] del objeto que implementa la capa [B]
    • línea 3: se solicitan datos a la instancia [ib]

    Ahora podemos ver que la clase de implementación [B1] de la capa B no aparece en ninguna parte del código de la capa [A]. Cuando la implementación [B1] se sustituya por una nueva implementación [B2], nada cambiará en el código de la clase [A]. Simplemente cambiamos los archivos de configuración de Spring para instanciar [B2] en lugar de [B1].

    La combinación de Spring y las interfaces de C# aporta una mejora decisiva al mantenimiento de la aplicación al hacer que las capas de la aplicación sean estancas. Esta es la solución que utilizaremos para una nueva versión de la aplicación [Impots].

    En casos sencillos, podemos partir de la capa [business] para descubrir las interfaces de la aplicación. Para que funcione, necesita:

    • aún no están disponibles. Son suministrados por la capa [ui], que los obtiene del usuario de la aplicación.

using System;
using System.Collections.Generic;
using System.IO;
using System.Text.RegularExpressions;
using Entites;
 
namespace Dao {
    class FileImpot : IImpotDao {
 
         // data file
        public string FileName { get; set; }
 
         // tax brackets
        public TrancheImpot[] TranchesImpot { get; private set; }
 
         // manufacturer
        public FileImpot(string fileName) {
             // save the file name
            FileName = fileName;
             // data
            List<TrancheImpot> listTranchesImpot = new List<TrancheImpot>();
            int numLigne = 1;
             // exception
            FileImpotException fe = null;
             // read the contents of the fileName file, line by line
            Regex pattern = new Regex(@"s*:\s*");
             // initially no error
            FileImpotException.CodeErreurs code = 0;
            try {
                using (StreamReader input = new StreamReader(FileName)) {
                    while (!input.EndOfStream && code == 0) {
                         // current line
                        string ligne = input.ReadLine().Trim();
                         // ignore empty lines
                        if (ligne == "")
                            continue;
                         // line broken down into three fields separated by :
                        string[] champsLigne = pattern.Split(ligne);
                         // do we have 3 fields?
                        if (champsLigne.Length != 3) {
                            code = FileImpotException.CodeErreurs.Ligne;
                        }
                         // 3-field conversions
                        decimal limite = 0, coeffR = 0, coeffN = 0;
                        if (code == 0) {
                            if (!Decimal.TryParse(champsLigne[0], out limite))
                                code = FileImpotException.CodeErreurs.Champ1;
                            if (!Decimal.TryParse(champsLigne[1], out coeffR))
                                code |= FileImpotException.CodeErreurs.Champ2;
                            if (!Decimal.TryParse(champsLigne[2], out coeffN))
                                code |= FileImpotException.CodeErreurs.Champ3;
                            ;
                        }
                         // mistake?
                        if (code != 0) {
                            // on note l'erreur
                            fe = new FileImpotException(String.Format("Ligne n° {0} incorrecte", numLigne)) { Code = code };
                        } else {
                             // the new tax bracket is memorized
                            listTranchesImpot.Add(new TrancheImpot() { Limite = limite, CoeffR = coeffR, CoeffN = coeffN });
                             // next line
                            numLigne++;
                        }
                    }
                }
            } catch (Exception e) {
                // on note l'erreur
                fe = new FileImpotException(String.Format("Erreur lors de la lecture du fichier {0}", FileName), e) { Code = FileImpotException.CodeErreurs.Acces };
            }
             // error to report?
            if (fe != null) {
                // on lance l'exception
                throw fe;
            } else {
                 // return the listImpot list in the tranchesImpot array
                TranchesImpot = listTranchesImpot.ToArray();
            }
        }
    }
}

         // tAX CALCULATION
        public int CalculerImpot(bool marié, int nbEnfants, int salaire) {
             // calculating the number of shares
            decimal nbParts;
            if (marié)
                nbParts = (decimal)nbEnfants / 2 + 2;
            else
                nbParts = (decimal)nbEnfants / 2 + 1;
            if (nbEnfants >= 3)
                nbParts += 0.5M;
             // calculation of taxable income & family quota

             // tAX CALCULATION

            int i = 0;
            while (QF > tranchesImpot[i].Limite)
                i++;
             // return result
            return (int)(revenu * tranchesImpot[i].CoeffR - nbParts * tranchesImpot[i].CoeffN);

    6.4.1. NUnit

    Hasta ahora, las pruebas realizadas para nuestras diversas aplicaciones se basaban en la verificación visual. Comprobábamos que lo que veíamos en la pantalla era lo esperado. Este método resulta inviable cuando hay muchas pruebas que realizar. Los seres humanos son propensos a la fatiga, y su capacidad para verificar las pruebas disminuye a medida que avanza el día. Por lo tanto, las pruebas deben automatizarse y aspirar a una intervención humana nula.

    Una aplicación evoluciona con el tiempo. Cada vez que evoluciona, debemos comprobar que la aplicación no «regresa», es decir, que sigue superando las pruebas funcionales que se realizaron cuando se escribió por primera vez. Estas pruebas se denominan pruebas de «no regresión». Una aplicación grande puede requerir cientos de pruebas. Se prueban todos los métodos de todas las clases de la aplicación. A estas pruebas se les denomina pruebas unitarias. Si no se han automatizado, pueden requerir la participación de muchos desarrolladores.

    Se han desarrollado herramientas para automatizar las pruebas. Una de ellas se llama NUnit. Está disponible en [http://www.nunit.org] :

    Para este documento se utilizó la versión 2.4.6 o superior (marzo de 2008). La instalación coloca un icono [1] en el escritorio:
