    10. Los subprocesos de ejecución

    10.1. La clase Thread

    Cuando se inicia una aplicación, esta se ejecuta en un flujo de ejecución denominado subproceso. La clase .NET que modela un subproceso es la clase System.Threading.Thread y tiene la siguiente definición:

    Constructores

    En los ejemplos siguientes solo utilizaremos los constructores [1,3]. El constructor [1] admite como parámetro un método con la firma [2], c.a.d. con un parámetro de tipo objeto y que no devuelve ningún resultado. El constructor [3] admite como parámetro un método con la firma [4], c.a.d. sin parámetros y que no devuelve ningún resultado.

    Propiedades

    Algunas propiedades útiles:

    1. Thread CurrentThread: propiedad estática que proporciona una referencia al hilo en el que se encuentra el código que ha solicitado esta propiedad
    2. string Name: el nombre del hilo
    3. bool IsAlive: indica si el hilo se está ejecutando o no.

    Métodos

    Los métodos más utilizados son los siguientes:

    1. Start(), Start(object obj): inicia la ejecución asíncrona del hilo, pasandole información en un tipo object si es necesario.
    2. Abort(), Abort(object obj): para forzar la finalización de un hilo
    3. Join(): el hilo T1 que ejecuta T2.Join queda bloqueado hasta que finalice el hilo T2. Existen variantes para poner fin a la espera tras un tiempo determinado.
    4. Sleep(int n): método estático; el hilo que ejecuta el método se suspende durante n milisegundos. De este modo, pierde el procesador, que se cede a otro hilo.

    Veamos una primera aplicación que pone de manifiesto la existencia de un hilo principal de ejecución, aquel en el que se ejecuta la función Main de una clase:

    10.2. Creación de subprocesos de ejecución

    Es posible tener aplicaciones en las que fragmentos de código se ejecutan de forma «simultánea» en diferentes subprocesos de ejecución. Cuando se dice que los subprocesos se ejecutan de forma simultánea, a menudo se comete un error de lenguaje. Si la máquina solo tiene un procesador, como suele ser el caso, los subprocesos comparten ese procesador: disponen de él, cada uno por turnos, durante un breve instante (unos milisegundos). Esto es lo que da la ilusión de paralelismo de ejecución. El tiempo asignado a un hilo depende de diversos factores, entre ellos su prioridad, que tiene un valor por defecto pero que también puede fijarse mediante programación. Cuando un hilo dispone del procesador, normalmente lo utiliza durante todo el tiempo que se le ha asignado. Sin embargo, puede liberarlo antes de tiempo:

    1. poniéndose en espera de un evento (Wait, Join)
    2. entrando en suspensión durante un tiempo determinado (Sleep)
    1. Un hilo T se crea en primer lugar mediante uno de los constructores presentados anteriormente, por ejemplo: 
    Thread thread=new Thread(Start);

    donde Start es un método que tiene una de las dos firmas siguientes:

    void Start();
void Start(object obj);

    La creación de un hilo no lo inicia.

    1. La ejecución del hilo T se inicia mediante T.Start(): el método Start pasado al constructor de T será entonces ejecutado por el hilo T. El programa que ejecuta la instrucción T.Start() no espera a que finalice la tarea T: pasa inmediatamente a la instrucción siguiente. Así, tenemos dos tareas que se ejecutan en paralelo. A menudo deben poder comunicarse entre sí para saber en qué punto se encuentra el trabajo común que deben realizar. Este es el problema de la sincronización de subprocesos.
    2. Una vez iniciado, el hilo T se ejecuta de forma autónoma. Se detendrá cuando el método Start que está ejecutando haya terminado su trabajo.
    3. Se puede forzar al subproceso T a que finalice:
      1. T.Abort() solicita al hilo T que finalice.
    4. También se puede esperar a que finalice su ejecución mediante T.Join(). Se trata de una instrucción bloqueante: el programa que la ejecuta queda bloqueado hasta que la tarea T haya terminado su trabajo. Es un método de sincronización.

    Examinemos el siguiente programa:

    
using System;
using System.Threading;
 
namespace Chap8 {
    class Program {
        public static void Main() {
            // init Hilo actual
            Thread main = Thread.CurrentThread;
            // dar un nombre al hilo
            main.Name = "Main";
 
            // creación de hilos de ejecución
            Thread[] tâches = new Thread[5];
            for (int i = 0; i < tâches.Length; i++) {
                // crear hilo i
                tâches[i] = new Thread(Affiche);
                // establecer el nombre del hilo
                tâches[i].Name =  i.ToString();
                // iniciar la ejecución del hilo i
                tâches[i].Start();
            }
 
            // fin de la mano
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}",main.Name,DateTime.Now);
        }
 
        public static void Affiche() {
            // mostrar inicio de ejecución
            Console.WriteLine("Début d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}",Thread.CurrentThread.Name,DateTime.Now);
            // silenciado durante 1 s
            Thread.Sleep(1000);
            // mostrar fin de carrera
            Console.WriteLine("Fin d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}", Thread.CurrentThread.Name, DateTime.Now);
        }
    }
}

    2. Líneas 13-21: se crean 5 subprocesos y se ejecutan. Las referencias de los subprocesos se almacenan en una matriz para poder recuperarlas posteriormente. Cada subproceso ejecuta el método «Affiche» de las líneas 27-35.
    3. línea 20: se inicia el subproceso n.º i. Esta operación es no bloqueante. El subproceso n.º i se ejecutará en paralelo al subproceso del método [Main] que lo ha iniciado.
    4. línea 24: el hilo que ejecuta el método [Main] finaliza.
    5. Líneas 27-35: el método [Affiche] muestra información. Muestra el nombre del hilo que lo ejecuta, así como las horas de inicio y fin de la ejecución.
    6. línea 31: cualquier subproceso que ejecute el método [Affiche] se detendrá durante 1 segundo. El procesador se cederá entonces a otro subproceso en espera del procesador. Al final del segundo de parada, el subproceso detenido será candidato al procesador. Lo obtendrá cuando le llegue el turno. Esto depende de diversos factores, entre ellos la prioridad de los demás subprocesos en espera del procesador.

    10.3. Interés de los hilos

    Ahora que hemos puesto de manifiesto la existencia de un hilo por defecto, el que ejecuta el método Main, y que sabemos cómo crear otros, detengámonos en el interés que tienen para nosotros los hilos y en las razones por las que los presentamos aquí. Hay un tipo de aplicaciones que se prestan bien al uso de hilos: las aplicaciones cliente-servidor de Internet. Las presentaremos en el capítulo siguiente. En una aplicación cliente-servidor de Internet, un servidor situado en una máquina S1 responde a las solicitudes de clients situados en máquinas remotas C1, C2, ..., Cn.

    Todos los días utilizamos aplicaciones de Internet que se ajustan a este esquema: servicios web, correo electrónico, consulta de foros, transferencia de archivos... En el esquema anterior, el servidor S1 debe atender a los clients Ci de forma simultánea. Si tomamos el ejemplo de un servidor FTP (Protocolo de Transferencia de Archivos) que entrega archivos a sus clients, sabemos que una transferencia de archivos puede tardar a veces varios minutos. Por supuesto, es impensable que un cliente monopolice por sí solo el servidor durante tanto tiempo. Lo que se suele hacer es que el servidor cree tantos subprocesos de ejecución como clients haya. Cada subproceso se encarga entonces de atender a un cliente concreto. Dado que el procesador se comparte cíclicamente entre todos los subprocesos activos de la máquina, el servidor dedica un poco de tiempo a cada cliente, garantizando así la simultaneidad del servicio.

    En la práctica, el servidor utiliza un grupo de subprocesos con un número limitado de subprocesos, por ejemplo, 50. El cliente número 51 debe entonces esperar.

    10.4. Intercambio de información entre subprocesos

    En los ejemplos anteriores, un hilo se inicializaba de la siguiente manera:

    Thread t=new Thread(Run);

    donde Run era un método con la siguiente firma:

    void Run();

    También es posible utilizar la siguiente firma:

    void Run(object obj);

    Esto permite transmitir información al hilo iniciado. Así,

    t.Start(obj1);

    iniciará el subproceso t, que ejecutará el método Run que se le ha asociado por defecto, pasando el parámetro efectivo obj1. He aquí un ejemplo:

    
using System;
using System.Threading;

namespace Chap8 {
    class Program4 {
        public static void Main() {
            // init Hilo actual
            Thread main = Thread.CurrentThread;
            // dar un nombre al hilo
            main.Name = "Main";
 
            // creación de hilos de ejecución
            Thread[] tâches = new Thread[5];
            Data[] data = new Data[5];
            for (int i = 0; i < tâches.Length; i++) {
                // crear hilo i
                tâches[i] = new Thread(Sleep);
                // establecer el nombre del hilo
                tâches[i].Name = i.ToString();
                // iniciar la ejecución del hilo i
                tâches[i].Start(data[i] = new Data { Début = DateTime.Now, Durée = i+1 });
            }
            // esperamos todos los hilos
            for (int i = 0; i < tâches.Length; i++) {
                // espera a que el hilo i termine de ejecutarse
                tâches[i].Join();
                // visualización de resultados
                Console.WriteLine("Thread {0} terminé : début {1:hh:mm:ss}, durée programmée {2} s, fin {3:hh:mm:ss}, durée effective {4}",
                    tâches[i].Name,data[i].Début,data[i].Durée,data[i].Fin,(data[i].Fin-data[i].Début));
            }        
            // fin de la mano
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}", main.Name, DateTime.Now);
        }
 
        public static void Sleep(object infos) {
            // el parámetro
            Data data = (Data)infos;
            // poner a dormir para Duración
            Thread.Sleep(data.Durée*1000);
            // fin de ejecución
            data.Fin = DateTime.Now;
        }
    }
 
    internal class Data {
        // otra información
        public DateTime Début { get; set; }
        public int Durée { get; set; }
        public DateTime Fin { get; set; }
    }
}
    1. líneas 45-50: la información de tipo [Data] pasada a los subprocesos:
      1. Inicio: hora de inicio de la ejecución del subproceso; la establece el subproceso iniciador
      2. Duración: duración en segundos del Sleep ejecutado por el subproceso lanzado, fijada por el subproceso lanzador
      3. Fin: hora de inicio de la ejecución del subproceso, fijada por el subproceso lanzador
    2. líneas 35-43: el método Sleep ejecutado por los subprocesos tiene la firma void Sleep(object obj). El parámetro efectivo obj será del tipo [Data] definido en la línea 45.
    3. líneas 15-22: creación de 5 subprocesos
    4. línea 17: cada hilo se asocia al método Sleep de la línea 35
    5. línea 21: se pasa un objeto de tipo [Data] al método Start, que inicia el hilo. En este objeto se ha anotado la hora de inicio de la ejecución del hilo, así como la duración en segundos durante la cual debe permanecer inactivo. Este objeto se almacena en la matriz de la línea 14.
    6. líneas 24-30: el hilo [Main] espera a que finalicen todos los hilos que ha iniciado.
    7. líneas 28-29: el hilo [Main] recupera el objeto data[i] del hilo n.º i y muestra su contenido.
    8. líneas 35-42: el método Sleep ejecutado por los subprocesos
    9. línea 37: se recupera el parámetro de tipo [Data]
    10. línea 39: se utiliza el campo Duración del parámetro para establecer la duración del Sleep
    11. línea 41: se inicializa el campo «Fin» del parámetro

    10.5. Accesos concurrentes a recursos compartidos

    10.5.1. Accesos concurrentes no sincronizados

    En el apartado sobre el intercambio de información entre subprocesos, la información solo se intercambiaba entre dos subprocesos y en momentos muy concretos. Se trataba de un clásico paso de parámetros. Existen otros casos en los que una información es compartida por varios subprocesos que pueden querer leerla o actualizarla al mismo tiempo. Entonces se plantea el problema de la integridad de dicha información. Supongamos que la información compartida es una estructura S con diversos datos I1, I2, ... In.

    • Un hilo T1 comienza a actualizar la estructura S: modifica el campo I1 y es interrumpido antes de haber completado la actualización de la estructura S
    • Un hilo T2 que recupera el procesador lee entonces la estructura S para tomar decisiones. Lee una estructura en un estado inestable: algunos campos están actualizados, otros no.

    A esta situación se le denomina acceso a un recurso compartido, en este caso la estructura S, y a menudo resulta bastante delicada de gestionar. Tomemos el siguiente ejemplo para ilustrar los problemas que pueden surgir:

    • una aplicación va a generar n subprocesos, siendo n un parámetro
    • el recurso compartido es un contador que deberá ser incrementado por cada subproceso generado
    • al final de la aplicación, se muestra el valor del contador. Por lo tanto, deberíamos obtener n.

    El programa es el siguiente:

    
using System;
using System.Threading;
 
namespace Chap8 {
    class Program {
 
        // variables de clase
        static int cptrThreads = 0;    // contador de hilos
 
        //mano
        public static void Main(string[] args) {
            // instrucciones de uso
            const string syntaxe = "pg nbThreads";
            const int nbMaxThreads = 100;
 
            // comprobar el número de argumentos
            if (args.Length != 1) {
                // error
                Console.WriteLine(syntaxe);
                // stop
                Environment.Exit(1);
            }
            // control de calidad de los argumentos
            int nbThreads = 0;
            bool erreur = false;
            try {
                nbThreads = int.Parse(args[0]);
                if (nbThreads < 1 || nbThreads > nbMaxThreads)
                    erreur = true;
            } catch {
                // error
                erreur = true;
            }
            // ¿Error?
            if (erreur) {
                // error
                Console.Error.WriteLine("Nombre de threads incorrect (entre 1 et 100)");
                // fin
                Environment.Exit(2);
            }
            // creación y generación de hilos
            Thread[] threads = new Thread[nbThreads];
            for (int i = 0; i < nbThreads; i++) {
                // creación
                threads[i] = new Thread(Incrémente);
                // nombrando
                threads[i].Name = "" + i;
                // lanzar
                threads[i].Start();
            }//para
            // esperando a que terminen los hilos
            for (int i = 0; i < nbThreads; i++) {
                threads[i].Join();

    10.5.3. La clase Mutex

    La clase System.Threading.Mutex también permite delimitar secciones críticas. Se diferencia de la cláusula lock en cuanto a la visibilidad:

    • la cláusula lock permite sincronizar subprocesos de una misma aplicación
    • la clase Mutex permite sincronizar subprocesos de diferentes aplicaciones.

    Utilizaremos el constructor y los siguientes métodos:

    public Mutex()
    crea un Mutex M
    public bool WaitOne()
    El subproceso T1 que ejecuta la operación M.WaitOne() solicita la propiedad del objeto de sincronización M. Si ningún subproceso tiene el control del mutex M (como ocurre inicialmente), se «cede» al subproceso T1 que lo ha solicitado. Si, poco después, un subproceso T2 realiza la misma operación, quedará bloqueado. De hecho, un mutex solo puede pertenecer a un hilo. Se desbloqueará cuando el hilo T1 libere el mutex M que mantiene. De este modo, varios hilos pueden quedar bloqueados a la espera del mutex M.
    public void ReleaseMutex()
    El hilo T1 que realiza la operación M.ReleaseMutex() cede la propiedad del mutex M. Cuando el hilo T1 pierda el procesador, el sistema podrá asignárselo a uno de los hilos que esperan el mutex M. Solo uno lo obtendrá a su vez, mientras que los demás que esperan M permanecerán bloqueados

    Un mutex M gestiona el acceso a un recurso compartido R. Un hilo solicita el recurso R mediante M.WaitOne() y lo devuelve mediante M.ReleaseMutex().     10.5.4. La clase AutoResetEvent

    Un objeto AutoResetEvent es una barrera que solo deja pasar un hilo a la vez, al igual que las dos herramientas anteriores, lock y Mutex. Se crea un objeto AutoResetEvent de la siguiente manera:

    AutoResetEvent barrière=new AutoresetEvent(bool état);

    El valor booleano estado indica si la barrera está cerrada (false) o abierta (true). Un hilo que desee atravesar la barrera lo indicará de la siguiente manera:

    barrière.WaitOne();
    • Si la barrera está abierta, el hilo pasa y la barrera se vuelve a cerrar tras él. Si había varios hilos esperando, se garantiza que solo uno pasará.
    • Si la barrera está cerrada, el hilo queda bloqueado. Otro hilo la abrirá cuando llegue el momento. Este momento depende totalmente del problema que se esté tratando. La barrera se abrirá mediante la operación: 
    barrière.Set();

    Puede ocurrir que un hilo quiera cerrar una barrera. Podrá hacerlo mediante:

    barrière.Reset();

    10.5.5. La clase Interlocked

    10.6. Accesos concurrentes a múltiples recursos compartidos

    10.6.1. Un ejemplo

    En nuestros ejemplos anteriores, un único recurso era compartido por los diferentes subprocesos. La situación puede complicarse si hay varios y estos dependen unos de otros. En particular, puede producirse una situación de interbloqueo. Esta situación, también denominada «deadlock», es aquella en la que dos subprocesos se esperan mutuamente. Consideremos las siguientes acciones que se suceden en el tiempo:

    1. un subproceso T1 obtiene la propiedad de un mutex M1 para acceder a un recurso compartido R1
    2. un hilo T2 obtiene la propiedad de un mutex M2 para acceder a un recurso compartido R2
    3. el hilo T1 solicita el mutex M2. Queda bloqueado.
    4. el subproceso T2 solicita el mutex M1. Queda bloqueado.

    En este caso, los subprocesos T1 y T2 se esperan mutuamente. Esta situación se da cuando los subprocesos necesitan dos recursos compartidos: el recurso R1 controlado por el mutex M1 y el recurso R2 controlado por el mutex M2. Una posible solución es solicitar ambos recursos al mismo tiempo mediante un único mutex M. Pero esto no siempre es posible si, por ejemplo, implica una larga ocupación de un recurso costoso. Otra solución es que un hilo que tenga M1 y no pueda obtener M2 libere entonces M1 para evitar el interbloqueo.

    • Tenemos una matriz en la que unos subprocesos depositan datos (los escritores) y otros los leen (los lectores).
    • Los escritores son iguales entre sí pero exclusivos: solo un escritor a la vez puede depositar sus datos en la matriz.
    • Los lectores son iguales entre sí pero exclusivos: solo un lector a la vez puede leer los datos depositados en la matriz.
    • Un lector solo puede leer los datos de la tabla cuando un escritor los ha depositado en ella, y un escritor solo puede depositar nuevos datos en la tabla cuando los que ya están allí han sido leídos por un lector.

    Se pueden distinguir dos recursos compartidos:

    • la tabla en escritura: solo un escritor a la vez debe tener acceso a ella.
    • la tabla en lectura: solo un lector a la vez debe tener acceso a ella.

    y un orden de uso de estos recursos:

    1. un lector siempre debe actuar después de un escritor.
    2. un escritor siempre debe ir después de un lector, excepto la primera vez.

    Se puede controlar el acceso a estos dos recursos con dos barreras de tipo AutoResetEvent:

    1. la barrera peutEcrire controlará el acceso de los escritores a la tabla.
    2. La barrera peutLire controlará el acceso de los lectores a la tabla.
    3. La barrera peutEcrire se creará inicialmente abierta, dejando pasar así a un primer escritor y bloqueando a todos los demás.
    4. La barrera peutLire se creará inicialmente cerrada, bloqueando a todos los lectores.
    5. Cuando un escritor haya terminado su trabajo, abrirá la barrera peutLire para dejar entrar a un lector.
    6. Cuando un lector haya terminado su trabajo, abrirá la barrera peutEcrire para dejar entrar a un escritor.

    10.6.2. La clase Monitor

    En el ejemplo anterior:

    • hay dos recursos compartidos que gestionar
    • para un recurso dado, los subprocesos son iguales.

    Cuando los subprocesos de escritura se bloquean en la instrucción peutEcrire.WaitOne, uno de ellos, cualquiera, se desbloquea mediante la operación peutEcrire.Set. Si la operación anterior debe abrir la barrera a un escritor en particular, las cosas se complican.

    Podemos considerar la analogía con un establecimiento que atiende al público en ventanillas, donde cada ventanilla está especializada. Cuando llega el cliente, coge un ticket en el dispensador de tickets para la ventanilla X y luego se sienta. Cada ticket está numerado y los clients son llamados por su número a través de un altavoz. Mientras espera, el cliente hace lo que quiere. Puede leer o dormitar. Cada vez le despierta el altavoz que anuncia que el n.º Y es llamado en la ventanilla X. Si se trata de él, el cliente se levanta y se dirige a la ventanilla X; si no, continúa con lo que estaba haciendo.

    Aquí podemos funcionar de manera análoga. Tomemos el ejemplo de los escritores:

    sus hilos están bloqueados
    le guichet se libère et le n° de l'écrivain suivant est appelé

    chaque écrivain regarde son n° et seul celui qui a le n° appelé
va au guichet. Les autres se remettent en attente.
    cada subproceso comprueba si es el elegido. Si es así, pasa la barrera. Si no, vuelve a ponerse en espera.

    La clase Monitor permite implementar este escenario.

    A continuación describimos una construcción estándar (patrón), propuesta en el capítulo Threading del libro C# 3.0 al que se hace referencia en la introducción de este documento, capaz de resolver los problemas de barrera con condición de entrada.

    1. En primer lugar, los subprocesos que comparten un recurso (la ventanilla, etc.) acceden a él a través de un objeto que llamaremos «token». Para abrir la barrera que conduce a la ventanilla, es necesario tener el token, y solo hay un token. Por lo tanto, los subprocesos deben pasarse el token entre sí. 
    object jeton=new object();
    1. Para ir a la ventanilla, los subprocesos solicitan primero el token: 
    Monitor.Enter(jeton);

    • Si el acceso a la ventanilla se realiza de forma no ordenada, c.a.d. en el caso de que no importe quién entre, la operación anterior es suficiente. El hilo que tiene el token va a la ventanilla. Si el acceso se realiza de forma ordenada, el hilo que tiene el token comprueba que cumple la condición para ir a la ventanilla: 
    while (! jeNeSuisPasCeluiQuiEstAttendu) {Monitor.Wait(jeton);}

Entonces volverá a comprobar si cumple la condición para ir a la ventanilla. La operación Monitor.Wait(token) que libera el token solo se puede realizar si el hilo es el propietario del token.     10.7. Los grupos de subprocesos

    Hasta ahora, para gestionar subprocesos:

    1. los creábamos mediante Thread T = new Thread(...)
    2. y luego los ejecutábamos mediante T.Start()

    En el capítulo «Bases de datos» vimos que con algunos SGBD era posible tener grupos de conexiones abiertas:

    1. se abren n conexiones al iniciar el grupo
    2. cuando un hilo solicita una conexión, se le asigna una de las conexiones abiertas del grupo
    3. cuando el hilo cierra la conexión, esta no se cierra, sino que se devuelve al grupo

    El uso de un grupo de conexiones es transparente a nivel del código. El interés radica en la mejora del rendimiento: abrir una conexión es costoso. Aquí, 10 conexiones abiertas pueden atender cientos de solicitudes.

    Existe un sistema similar para los hilos:

    1. se crean min subprocesos al iniciar el grupo. El valor de min se establece con el método ThreadPool.SetMinThreads(min1,min2). Un grupo de subprocesos puede utilizarse para ejecutar tareas bloqueantes o no bloqueantes, denominadas asíncronas. El primer parámetro min1 establece el número de subprocesos bloqueantes, y el segundo, min2, el número de subprocesos asíncronos. Los valores actuales de estos dos parámetros pueden obtenerse mediante ThreadPool.GetMinThreads(out min1,out min2).
    2. Si este número no es suficiente, el grupo creará otros subprocesos para responder a las solicitudes hasta el límite de subprocesos máximos. El valor de max se establece con el método ThreadPool.SetMaxThreads(max1,max2). Ambos parámetros tienen el mismo significado que en el método SetMinThreads. Los valores actuales de estos dos parámetros se pueden obtener mediante ThreadPool.GetMaxThreads(out max1,out max2). Cuando se alcancen los max1 subprocesos, las solicitudes de subprocesos para tareas bloqueantes quedarán en espera de un subproceso libre en el grupo.

    Un grupo de subprocesos ofrece diversas ventajas:

    1. al igual que con el grupo de conexiones, se ahorra tiempo en la creación de subprocesos: 10 subprocesos pueden atender cientos de solicitudes.
    2. se garantiza la seguridad de la aplicación: al fijar un número máximo de subprocesos, se evita que la aplicación se sature por un exceso de solicitudes. Estas se pondrán en cola.

    Para asignar una tarea a un hilo del grupo, se utiliza uno de los dos métodos:

    1. ThreadPool.QueueWorkItem(WaitCallBack)
    2. ThreadPool.QueueWorkItem(WaitCallBack,object)

    donde WaitCallBack es cualquier método con la firma void WaitCallBack(object). El método 1 solicita a un subproceso que ejecute el método WaitCallBack sin pasarle ningún parámetro. El método 2 hace lo mismo, pero pasando un parámetro de tipo object al método WaitCallBack.

    10.8. La clase BackgroundWorker

    10.8.1. Ejemplo 1

    La clase BackgroundWorker pertenece al espacio de nombres [System.ComponentModel]. Se utiliza como un hilo, pero presenta características que pueden hacerla, en algunos casos, más interesante que la clase [Thread]:

    • emite los siguientes eventos:
    • DoWork: un hilo ha solicitado la ejecución de BackgroundWorker
    • ProgressChanged: el objeto BackgroundWorker ha ejecutado el método ReportProgress. Este sirve para indicar un porcentaje de ejecución.
    • RunWorkerCompleted: el objeto BackgroundWorker ha finalizado su trabajo. Puede haberlo finalizado normalmente, por cancelación o por excepción.

    Estos eventos hacen que BackgroundWorker resulte útil en las interfaces gráficas: una tarea larga se asignará a un BackgroundWorker, que podrá informar de su progreso con el evento ProgressChanged y de su finalización con el evento RunWorkerCompleted. El trabajo que debe realizar el BackgroundWorker se llevará a cabo mediante un método que se habrá asociado al evento DoWork.

    1. Es posible solicitar su cancelación. En una interfaz gráfica, el usuario podrá así cancelar una tarea larga.
    • Los objetos BackgroundWorker pertenecen a un grupo y se reciclan según sea necesario. Una aplicación que necesite un objeto BackgroundWorker lo obtendrá del grupo, que le proporcionará un subproceso ya existente pero no utilizado. El hecho de reciclar así los subprocesos, en lugar de crear uno nuevo cada vez, mejora el rendimiento.

    10.9. Datos locales de un hilo

    10.9.1. El principio

    Consideremos una aplicación de tres capas:

    Supongamos que la aplicación es multiusuario, una aplicación web, por ejemplo. Cada usuario es atendido por un hilo dedicado exclusivamente a él. El ciclo de vida del hilo es el siguiente:

    • el hilo se crea o se solicita a un grupo de hilos para satisfacer una solicitud de un usuario
    • si esta solicitud requiere datos, el hilo ejecutará un método de la capa [ui] que llamará a un método de la capa [metier], el cual, a su vez, llamará a un método de la capa [dao].
    • El hilo devuelve la respuesta al usuario. A continuación, desaparece o se recicla en un grupo de hilos.

    En la operación 2, puede ser interesante que el hilo tenga datos propios, c.a.d, que no se compartan con los demás hilos. Estos datos podrían, por ejemplo, pertenecer al usuario concreto al que da servicio el hilo. Estos datos podrían entonces utilizarse en las diferentes capas [ui, metier, dao].

    La clase Thread permite este escenario gracias a una especie de diccionario privado en el que las claves serían de tipo LocalDataStoreSlot:

    crea una entrada en el diccionario privado del hilo para la clave name.
    asocia el valor data a la clave name del diccionario privado del hilo
    Recupera el valor asociado a la clave name del diccionario privado del hilo

    Un ejemplo de uso podría ser el siguiente:

    1. para crear un par (clave, valor) asociado al hilo actual: 
    Thread.SetData(Thread.GetNamedDataSlot("clé"),valeur);
    1. para recuperar el valor asociado a la clave: 
    Thread.GetData(Thread.GetNamedDataSlot("clé"));

    Posteriormente, para otra aplicación, surge la necesidad de eliminar una lista de artículos guardada en una lista, siempre dentro de una transacción. Se observa que, para responder a diferentes necesidades de negocio, la capa [dao] se verá obligada a crecer. Se puede optar por otra vía:

    1. incluir en la capa [dao] solo las operaciones básicas InsertArticle, DeleteArticle, UpdateArticle, SelectArticle, SelectArticles
    2. trasladar a la capa [métier] las operaciones de actualización simultánea de varios artículos. Estas utilizarían las operaciones elementales de la capa [dao].

    La ventaja de esta solución es que la misma capa [dao] podría utilizarse sin cambios con diferentes capas [metier]. Sin embargo, plantea una dificultad en la gestión de la transacción que agrupa actualizaciones que deben realizarse de forma atómica en la base:

    • la transacción debe ser iniciada por la capa [metier] antes de que esta llame a los métodos de la capa [dao]
    • los métodos de la capa [dao] deben conocer la existencia de la transacción para poder participar en ella si existe
    • la transacción debe ser finalizada por la capa [métier].

    Para que los métodos de la capa [dao] conozcan la existencia de una posible transacción en curso, se podría añadir la transacción como parámetro de cada método de la capa [dao]. Este parámetro aparecerá entonces en la firma de los métodos de la interfaz, lo que la vinculará a una fuente de datos concreta: la base de datos. Los datos locales del hilo nos ofrecen una solución más elegante: la capa [métier] colocará la transacción en los datos locales del hilo y será allí donde la capa [dao] la recuperará. Por lo tanto, no es necesario modificar la firma de los métodos de la capa [dao].

    Implementación de la capa [metier]

    La implementación de negocio de la interfaz IMetier será la siguiente:

    
using System.Collections.Generic;
using System.Data;
using System.Data.SqlServerCe;
using System.Threading;
 
namespace Chap8 {
    public class Metier : IMetier {
        // capa [dao]
        public IDao Dao { get; set; }
        // cadena de conexión
        public string ConnectionString { get; set; }
 
        // insertar una matriz de elementos dentro de una transacción
        public void InsertArticlesInTransaction(Article[] articles) {
            // crear la conexión a la base de datos
            using (SqlCeConnection connexion = new SqlCeConnection(ConnectionString)) {
                // conexión de apertura
                connexion.Open();
                // transacción
                SqlCeTransaction transaction = null;
                try {
                    // inicio de la transacción
                    transaction = connexion.BeginTransaction(IsolationLevel.ReadCommitted);
                    // registrar la transacción en el hilo
                    Thread.SetData(Thread.GetNamedDataSlot("transaction"), transaction);
                    // inserción de artículos
                    foreach (Article article in articles) {
                        Dao.InsertArticle(article);
                    }
                    // validar la transacción
                    transaction.Commit();
                } catch {
                    // deshacemos la transacción
                    if (transaction != null)
                        transaction.Rollback();
                }
            }
        }
 
        // insertar una matriz de elementos sin transacción
        public void InsertArticlesOutOfTransaction(Article[] articles) {
            // inserción de artículos
            foreach (Article article in articles) {
                Dao.InsertArticle(article);
            }
        }
 
        // lista de artículos
        public List<Article> GetAllArticles() {
            return Dao.GetAllArticles();
        }
        // eliminar todos los elementos
        public void DeleteAllArticles() {
            Dao.DeleteAllArticles();
        }
    }
}

    La clase tiene las siguientes propiedades:

    • línea 9: una referencia a la capa [dao]
    • línea 11: la cadena de conexión que permite conectarse a la base de datos de artículos

    Solo comentaremos el método InsertArticlesInTransaction, que es el único que presenta dificultades:

    • línea 16: se crea una conexión con la base de datos
    • línea 18: se abre
    • línea 23: se crea una transacción
    • línea 25: se registra en los datos locales del hilo, asociada a la clave «transaction»
    • líneas 27-29: se llama al método de inserción unitaria de la capa [dao] para cada artículo que se va a insertar
    • líneas 21 y 32: toda la inserción de la tabla se controla mediante un try / catch
    • línea 31: si se llega hasta aquí, es que no se ha producido ninguna excepción. Entonces se valida la transacción.
    • líneas 34-35: se ha producido una excepción, se deshace la transacción
    • línea 37: se sale de la cláusula using. La conexión abierta en la línea 18 se cierra automáticamente.

    Implementación de la capa [dao]

    La implementación Dao de la interfaz IDao será la siguiente:

    
using System.Collections.Generic;
using System.Data;
using System.Data.SqlServerCe;
using System.Threading;
 
namespace Chap8 {
    public class Dao : IDao {
        // cadena de conexión
        public string ConnectionString { get; set; }
        // solicita
        public string InsertText { get; set; }
        public string DeleteAllText { get; set; }
        public string GetAllText { get; set; }
 
        // implementación de la interfaz

        // insertar artículo
        public int InsertArticle(Article article) {
            // ¿hay una transacción en curso?
            SqlCeTransaction transaction = Thread.GetData(Thread.GetNamedDataSlot("transaction")) as SqlCeTransaction;
            // recuperar o crear una conexión
            SqlCeConnection connexion = null;
            if (transaction != null) {
                // recuperar la conexión
                connexion = transaction.Connection as SqlCeConnection;
            } else {
                // créalo
                connexion = new SqlCeConnection(ConnectionString);
                connexion.Open();
            }
            try {
                // preparación de la orden de inserción
                SqlCeCommand sqlCommand = new SqlCeCommand();
                sqlCommand.Transaction = transaction;
                sqlCommand.Connection = connexion;
                sqlCommand.CommandText = InsertText;
                sqlCommand.Parameters.Add("@nom", SqlDbType.NVarChar, 30);
                sqlCommand.Parameters.Add("@prix", SqlDbType.Money);
                sqlCommand.Parameters.Add("@sa", SqlDbType.Int);
                sqlCommand.Parameters.Add("@sm", SqlDbType.Int);
                sqlCommand.Parameters["@nom"].Value = article.Nom;
                sqlCommand.Parameters["@prix"].Value = article.Prix;
                sqlCommand.Parameters["@sa"].Value = article.StockActuel;
                sqlCommand.Parameters["@sm"].Value = article.StockMinimum;
                // ejecución
                return sqlCommand.ExecuteNonQuery();
            } finally {
                // si no estaba en una transacción, cierra la conexión
                if (transaction == null) {
                    connexion.Close();
                }
            }
        }
 
        // lista de artículos
        public List<Article> GetAllArticles() {
...
        }
 
        // eliminar artículos
        public void DeleteAllArticles() {
...
        }
    }
}

                new SqlCeCommand(DeleteAllText, connexion).ExecuteNonQuery();
            }

    10.9.3. Conclusión

    El ejemplo anterior ha mostrado la utilidad de los datos locales de un subproceso para la gestión de transacciones. No debe reproducirse tal cual. Frameworks como Spring, Nhibernate, etc., utilizan esta técnica, pero la hacen aún más transparente: la capa [metier] puede utilizar transacciones sin que la capa [dao] tenga por qué saberlo. Por lo tanto, no hay ningún objeto Transaction en el código de la capa [dao]. Esto se consigue mediante una técnica de proxy denominada AOP (programación orientada a aspectos). Una vez más, no podemos sino animar al lector a utilizar estos marcos de trabajo.
